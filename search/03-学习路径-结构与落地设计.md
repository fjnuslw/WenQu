# 学习路径板块 · 结构与落地设计

> 前置：`01-渠道与方向调研.md`（方向与约束）、`02-资源清单.md`（141 条已核验资源）。
> 本文解决「资源怎么组织成能走完的路径」，以及「数据结构、进度模型、与既有模块怎么咬合」。

## 1. 一句话定位

学习路径不是收藏夹，而是**带验收标准的执行清单**：告诉你下一步做什么、做完拿什么产出、怎么证明做完了，并把产出顺着已有的题库/复习/项目拷打链路接下去。

网上的路线图失败在三件事：只给链接不给顺序、只给顺序不给验收、做完没有沉淀。本设计逐一对应：

| 常见失败 | 本设计的对策 |
|---|---|
| 只给链接不给顺序 | 路径 → 阶段 → 节点三级有序结构，节点间显式依赖（`requires`） |
| 只给顺序不给验收 | 每个节点带 `acceptance[]`：可判定的完成判据（跑通 X / 刷完 N 题 / 写出 Y） |
| 做完没有沉淀 | 节点完成可一键生成复习卡回流 F6；实战节点的产出物直接送进 F4 项目拷打 |

## 2. 数据结构

### 2.1 目录（catalog）—— 受版本控制，不落库

放在 `apps/api/src/getoffer/paths/data/paths.json`，由 `search/_raw/inventory.json` 生成后人工校正。

**为什么不落库**：目录是「内容」，需要 diff、评审、回滚，Git 天然合适；落库则每次改文案都要写迁移，且无法 code review。库里只存**用户状态**。

```jsonc
{
  "version": "2026-08-30",
  "paths": [
    {
      "slug": "llm-app",
      "title": "大模型应用",
      "subtitle": "用现成模型把业务跑通并验证效果",
      "order": 1,
      "accent": "violet",
      "icon": "Bot",
      "for_who": "目标大模型应用开发 / AI Agent 工程岗",
      "weeks": "10–14 周",
      "outcomes": ["能独立交付带评测闭环的 RAG 系统", "能讲清 Agent 编排与 MCP 工具生态"]
    }
  ],
  "stages": [
    {
      "id": "llm-app-3",
      "path": "llm-app",
      "order": 3,
      "title": "RAG 全链路",
      "goal": "从文档到可评测的问答系统，能定位召回问题并给出改进依据",
      "weeks": "2–3 周"
    }
  ],
  "nodes": [
    {
      "id": "llm-app-3-1",
      "stage": "llm-app-3",
      "order": 1,
      "title": "跑通最小 RAG：加载 → 切分 → 检索 → 生成",
      "objective": "不依赖任何高级特性，先把链路端到端跑通，建立对每一步输入输出的手感",
      "deliverable": "一个可对本地 20 篇文档问答的脚本，支持打印命中片段",
      "acceptance": [
        "对 10 个自拟问题，能打印出命中的原文片段与相似度分数",
        "换 3 种 chunk_size/overlap 对比召回结果，记录差异"
      ],
      "resources": ["app-3-1", "app-3-2"],
      "hours": 6,
      "related": { "tags": ["RAG"], "question_kind": null }
    }
  ],
  "resources": [ /* 与 inventory.json 同构：id/title/kind/url/repo/stars/license/pushed_at/priority/why */ ]
}
```

**加载约束（对齐 spec §7）**：
- 启动时用 Pydantic 完整校验，缺字段/引用了不存在的 resource id → 抛 `PathsCatalogError`，**不做静默降级**。
- 校验规则包含：节点 `stage` 必须存在、`resources[]` 的 id 必须在资源表中、阶段内 `order` 不重复。

### 2.2 进度（progress）—— 落库，两表

| 表 | 字段 | 说明 |
|---|---|---|
| `learning_enrollments` | `id`, `path_slug`(unique), `target_role`, `daily_minutes`, `started_on`, `target_on`, `updated_at` | 路径订阅与目标设定，驱动「今日该做什么」 |
| `learning_node_progress` | `id`, `node_id`(unique), `status`, `note`, `updated_at` | 节点状态：`todo` / `doing` / `done` / `skipped` |

- 单用户形态，不引 user 外键（与项目当前 `users` 表未强制关联的现状一致）。
- `node_id` 是目录里的字符串 id，不是数据库外键 —— 目录可随时增删节点而不会破坏历史进度（删掉的节点状态变成孤儿，由前端忽略而非报错）。

### 2.3 派生字段（不存，实时算）

- 路径完成度 = `done / (总节点 - skipped)`
- 阶段完成度同理
- 「今日该做什么」= 取已订阅路径中第一个非 done 节点，按 `daily_minutes` 与节点 `hours` 估算需要几天

## 3. 节点设计原则

1. **一个节点一次坐下来能推进**。单节点 `hours` 控制在 2–10 小时，超过就拆。
2. **验收判据必须可判定**。反例：「理解 Transformer」；正例：「能徒手写出多头注意力的维度变换，并解释 mask 的作用」。
3. **产出物优先于输入量**。节点写「交付什么」而不是「看多少小时视频」。
4. **必学资源每节点 ≤ 3 条**。资源过多等于没有资源，其余放选修/参考。
5. **实战节点必须含评测**。来自调研结论 D6（纯 RAG Demo 已烂大街，面试要的是效果验证）。
6. **节点与题库标签挂钩**，让「学完就练」成为默认动作，而不是两个割裂的模块。

### 3.1 节点规模

| 路径 | 阶段数 | 节点数 | 必学资源引用 |
|---|---|---|---|
| L0 共用前置 | 2 | 5 | 3 |
| L1 大模型应用 | 6 | 27 | 21 |
| L2 大模型算法 | 6 | 30 | 22 |
| L3 大模型开发 | 6 | 23 | 14 |
| L4 手撕算法 | 6 | 24 | 23 |
| **合计** | **26** | **109** | **83 次引用（去重后 51 个不同资源）** |

> 落地时节点数从设计稿的 93 增到 109：写节点的过程中发现「预训练」「推理优化」几处
> 拆成单个节点会超过 10 小时上限，按原则 1 拆开了。必学资源引用 83 次是因为同一资源
> （如 LangGraph、vLLM）会被多个节点引用，去重后仍是 51 个。

## 4. 与既有模块的咬合点

这是本板块真正的价值所在 —— 不新造一个知识孤岛。

| 咬合方向 | 机制 | 复用现有能力 |
|---|---|---|
| 节点 → 题库 | 节点 `related.tags` 对应 F2 的 12 标签族，节点卡上「去练这道题」直接跳 `/bank?tag=RAG` | F2 题库筛选与检索 |
| 节点 → 复习 | 节点完成时可一键生成 `ReviewItem`（source=`path`，source_ref=node_id），进入 SM-2 队列 | F6 复习队列 |
| 实战节点 → 项目拷打 | 应用线/开发线的产出物是本地项目目录，直接送进 `/grilling` 做 AI 备课与拷打 | F4 项目拷打 |
| 手撕线 → 题单 | L4 阶段 4 的题单与 F2 中 `kind=手撕` 的题目对齐，刷题记录走既有自测/SM-2 | F2 + F6 |
| 面经 → 题单优先级 | F1 面经频率榜成熟后，用它回灌 L4 阶段 4 的「投哪家刷哪家」 | F1（后期） |
| 路径 → 工作台 | 仪表盘新增「学习路径进度」卡，显示已订阅路径的完成度与今日节点 | 现有 dashboard |

**明确的边界**：学习路径**不复制**任何题目正文与教程内容，只维护「去哪里学、学到什么算过关」。License 风险因此局限在外链层面（沿用 spec §10 门禁）。

## 5. API 契约（草案）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/paths` | 目录总览：路径卡片 + 每路径进度聚合（done/total/当前节点） |
| `GET` | `/api/paths/{slug}` | 路径详情：阶段树 + 节点 + 内嵌资源 + 各节点状态 |
| `PUT` | `/api/paths/{slug}/enroll` | 订阅/更新目标（target_role / daily_minutes / target_on），幂等 upsert |
| `PUT` | `/api/paths/nodes/{node_id}/progress` | 更新节点状态（status/note），幂等 upsert |
| `GET` | `/api/paths/plan/today` | 今日计划：已订阅路径的当前节点 + 预计耗时 |

- 全部走类型化错误：路径不存在 → `NotFound`；node_id 不在目录中 → `NotFound`（不做「自动创建节点」的静默兜底）。
- 目录只读，无写接口 —— 改目录走 Git。

## 6. UI 结构

### 6.1 `/paths` 总览

- 顶部：一句定位 + 统计（4 条路径 / N 个节点 / 已完成 X）
- 主体：4 张路径卡（+ L0 前置卡），每张含：标题、适合谁、参考周期、进度环、必学节点数、进入按钮
- 未订阅的路径卡显示「订阅」按钮，订阅后卡上出现目标日期与今日剩余

### 6.2 `/paths/{slug}` 详情

- 左栏：阶段时间线（可折叠），每阶段显示进度点与周数；点击滚动/筛选右栏
- 右栏：节点卡片流，每卡片含
  - 标题 + 目标 + 预计小时
  - 产出物（deliverable）
  - 验收判据（可勾选 checklist，勾满即视为完成，也可手动标 done）
  - 资源 chips：必学在前，选修/参考在后；hover 显示 star/license/最近推送
  - 操作：标记状态、写笔记、生成复习卡、相关题库练习
- 顶部订阅条：目标岗位 / 每日投入 / 目标日期

### 6.3 设计基调

沿用 spec §6：暗色优先、键盘优先、信息密度高。进度环与阶段时间线用现有 `accent / ok / warn` 语义色；资源 chip 的 license 异常（GPL/AGPL 或未标注）用 `warn` 提示。

## 7. 落地分期

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **P1 骨架** | 目录数据 + `/api/paths*` 只读与进度接口 + `/paths` 与 `/paths/{slug}` 两个页面 + 侧边栏入口 | 四条路径可浏览、可勾选进度、刷新后保持 |
| **P2 咬合** | 节点 → 题库跳转、节点 → 复习卡生成、今日计划、仪表盘进度卡 | 学完一个节点能立刻练题并进入复习队列 |
| **P3 个性化** | 基于简历 + JD 推荐路径与跳过建议；面经频率榜回灌手撕题单 | 路径能根据目标岗位自动裁剪 |

## 8. 未决问题

| # | 问题 | 倾向方案 |
|---|---|---|
| 1 | 节点数量与维护成本：109 个节点的验收判据需要持续维护 | 先保证 L1/L4 两条主线质量，L2/L3 允许阶段性粗粒度 |
| 2 | 目录改版后旧进度如何迁移 | node_id 保持稳定；废弃节点标 `deprecated` 而非删除，前端折叠显示 |
| 3 | 是否需要「跳过」语义 | 保留 `skipped`，但完成度分母剔除，避免"跳过刷进度" |
| 4 | 资源过期自动下架 vs 人工复核 | 只标 `stale` 提示，不自动下架（避免误杀经典但低频更新的项目） |
